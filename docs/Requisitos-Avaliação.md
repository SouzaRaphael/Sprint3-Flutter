Objetivo

Desenvolver uma versão funcional do aplicativo Android em Flutter e navegável, contendo as principais telas e fluxos do produto utilizando dados mockados para representar o comportamento principal da solução proposta. Não será exigida integração com API, Firebase, banco de dados local ou backend nesta Sprint. 

Entrega única – Projeto com README obrigatório – 100 pontos

A entrega deverá contemplar:

1. Identificação do projeto, equipe e evidências no README – 5 pontos

O grupo deverá apresentar de forma clara e explícita, obrigatoriamente no arquivo README.md do repositório:

Nome do projeto;
Nome da equipe;
Integrantes;
Breve descrição do objetivo do aplicativo;
Link do repositório GitHub do projeto;
Prints das principais telas do aplicativo;
Breve descrição de cada tela apresentada;
Instruções básicas para executar o projeto.

O arquivo README.md deve estar na raiz do projeto e precisa permitir que o avaliador identifique rapidamente o projeto, a equipe responsável, a proposta da aplicação e as telas implementadas.

As imagens inseridas no README.md devem representar o aplicativo rodando. Prints de Figma, slides ou protótipos visuais não substituem as telas implementadas no projeto.

A ausência dessas informações no README.md poderá gerar desconto neste critério, mesmo que elas apareçam em outros locais da entrega. 

2. Interface e experiência do usuário – 30 pontos

O aplicativo deverá apresentar telas organizadas, navegáveis e coerentes com a proposta da solução.

A entrega deve conter:

Tela inicial ou tela de apresentação do aplicativo;
Telas principais do fluxo do usuário;
Componentes visuais consistentes;
Textos compreensíveis;
Organização visual adequada;
Aplicação de princípios básicos de usabilidade;

3. Navegação entre telas – 20 pontos

O aplicativo deverá possuir navegação funcional entre as telas principais.

A entrega deve demonstrar:

Uso de navegação entre diferentes telas;
Fluxo coerente entre início, listagem, detalhes, formulário ou outras telas relevantes;
Passagem de parâmetros entre telas, quando fizer sentido;
Botões e ações funcionando;
Retorno visual para o usuário após alguma interação;

Exemplo: ao clicar em um item mockado de uma lista, o aplicativo deve abrir uma tela de detalhes correspondente àquele item.

A navegação precisa demonstrar que o aplicativo possui fluxo de uso, não apenas telas criadas de forma independente. 

4. Dados mockados e simulação da solução – 15 pontos

O aplicativo deverá utilizar dados mockados para simular o funcionamento da solução.

A entrega deve conter:

Criação de classes ou modelos de dados coerentes com o projeto;
Lista de dados mockados relacionados ao problema escolhido;
Exibição desses dados nas telas do aplicativo;
Simulação de fluxos importantes usando os dados mockados;
Dados realistas, organizados e compatíveis com o contexto da solução;
Evitar textos genéricos como “Item 1”, “Teste”, “Lorem ipsum” ou dados sem sentido.

Os dados mockados devem ajudar a demonstrar como o aplicativo funcionaria em um cenário real.

Nesta Sprint, não será exigida integração com API, Firebase, banco de dados local ou backend. Porém, os dados mockados devem estar organizados no código, preferencialmente em classes, objetos, listas ou arquivos separados, evitando dados espalhados diretamente nas telas. 

5. Arquitetura e organização do código – 15 pontos

O projeto deverá apresentar uma estrutura de código organizada, legível e coerente com boas práticas de desenvolvimento de aplicativos.

A entrega deve contemplar:

Separação mínima de responsabilidades;
Organização por pacotes, camadas ou pastas;
Nomes claros para classes, funções, telas e componentes;
Evitar excesso de código concentrado em uma única classe ou arquivo;
Componentização de telas e elementos visuais;
Código compreensível para manutenção e evolução.

6. Evidências de funcionamento – 10 pontos

A entrega deverá incluir evidências claras de que o aplicativo foi executado.

O grupo deverá entregar:

Vídeo da navegação do aplicativo mostrando as funcionalidades;
Link inserido no README.md;

7. Repositório, versionamento e qualidade da entrega – 5 pontos

O projeto deverá estar em um repositório organizado.

Serão avaliados:

Repositório acessível;
Commits realizados ao longo do desenvolvimento;
README com informações completas;
Estrutura limpa do projeto;
Projeto abrindo corretamente;
Histórico de contribuição compatível com o trabalho em grupo.

*  Commits feitos apenas no último momento poderão ser considerados indício de baixa organização do processo de desenvolvimento. 

Formato de entrega

A entrega deverá ser realizada em arquivo .ZIP, contendo:

Projeto completo

O projeto deverá estar completo, organizado e apto a ser aberto e executado.
O projeto deve conter todos os arquivos necessários para execução, incluindo código-fonte, configurações, dependências e estrutura de pastas. Caso o projeto não compile/rode a nota será 0.
Readme precisa estar na raíz do projeto conforme já descrito.



IMPORTANTE: Entregas fora do formato solicitado será avaliada como 0.
